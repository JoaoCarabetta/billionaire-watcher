# ADR-0003: dbt-bigquery in this repo

## Status

Accepted

## Date

2026-08-24

## Context

The billionaire-watcher project requires SQL transformations to:
- Stage raw source data (RF CNPJ, CVM FRE, TSE donations)
- Match freeze persons to entities in source datasets
- Generate Facts (structured JSONL records with sources and citations)

dbt (data build tool) is the standard for SQL-based transformation pipelines. The decision is where the dbt project lives and which adapter to use.

Considerations:
- **Repository**: Should dbt live in `billionaire-watcher` (public) or a separate `data-analysis` repo (private)?
- **Adapter**: `dbt-bigquery`, `dbt-duckdb`, or another?
- **Layers**: How to organize models (staging, intermediate, facts)?
- **Tests**: What data quality checks are essential?
- **Exposures**: How does the dbt project relate to the Astro static site?
- **Output**: How are Facts exported from BigQuery to R2?

## Decision

### dbt project location

The dbt project lives **in this repository** (`billionaire-watcher`), not in a separate private `data-analysis` repo.

**Rationale**:
- The dbt models define the transformation logic that produces the public Facts JSONL
- Keeping models, Astro code, and documentation in one repo simplifies versioning and cross-references
- Contributors can see the full pipeline: source → transform → presentation

### Adapter

**`dbt-bigquery`** is the chosen adapter.

**Rationale**:
- BigQuery is the transform engine (ADR-0001)
- `dbt-bigquery` is mature, well-documented, and integrates with Base dos Dados
- Base dos Dados tables are already in BigQuery

### Layers

dbt models are organized into three layers:

1. **Staging** (`models/staging/`):
   - Light transformations: renaming, type casting, basic filtering
   - One staging model per source table (e.g., `stg_rf_cnpj__empresas`, `stg_tse__receitas_candidato`)
   - Source freshness tests

2. **Match** (`models/match/`):
   - Join freeze persons to source entities
   - Normalize CNPJ grain (8 vs. 14 digits)
   - CPF masking and matching logic
   - Deduplication and entity resolution

3. **Facts** (`models/facts/`):
   - One row per fact, with columns: `fact_id`, `person_id`, `fact_type`, `value`, `source_publisher`, `source_locator`, `source_retrieved_at`
   - Grain: one fact per assertion (e.g., "João holds 15% of CNPJ 12345678")
   - Output format: denormalized, ready for JSONL export

### Tests

Essential data quality tests:

- **Uniqueness**: `fact_id` must be unique in `facts` models
- **Not null**: `source_publisher`, `source_locator`, `source_retrieved_at` must never be null
- **Relationships**: `person_id` in `facts` must exist in `freeze` persons
- **Accepted values**: `fact_type` must be one of a known enum (e.g., `ownership`, `donation`, `listed_company_role`)

Custom tests (via `tests/` directory or dbt packages) for:
- CNPJ format validation (8-digit `cnpj_basico`, 14-digit full CNPJ, alphanumeric)
- Masked CPF format (`***.123.456-**`)

### Exposures

The dbt project declares an **exposure** for the Astro static site:

```yaml
exposures:
  - name: astro_static_site
    type: dashboard
    owner:
      name: billionaire-watcher maintainers
    depends_on:
      - ref('facts')
    description: |
      Static HTML dossiers generated by Astro from Facts JSONL published to R2.
```

This documents the dependency: Astro consumes `facts` via R2.

### Output: Export to R2

Facts are exported from BigQuery to R2 in two steps:

1. **BigQuery → GCS**: Use `bq extract` or dbt post-hook to export `facts` table to GCS as newline-delimited JSON (NDJSON/JSONL), partitioned by `person_id`:
   - `gs://bucket/facts/{date}/{person}.jsonl`
   - `gs://bucket/facts/latest/{person}.jsonl`

2. **GCS → R2**: Use `rclone` or a Python script to sync from GCS to R2.

**Critical constraint**: The HTML build does **not** query BigQuery. Astro reads pre-exported JSONL from R2. This decouples the static site from BigQuery credentials and query costs (ADR-0001).

## Consequences

### Positive

- dbt models, Astro code, and ADRs in one repo simplify cross-references and versioning
- `dbt-bigquery` leverages mature tooling and Base dos Dados integration
- Three-layer architecture (staging → match → facts) is standard and maintainable
- Tests enforce data quality before Facts are published
- Exposures document the dbt → Astro dependency
- Facts JSONL format is stable and decoupled from BigQuery

### Negative

- dbt models in the public repo expose transformation logic (but source data and credentials remain private)
- Export pipeline (BQ → GCS → R2) adds operational complexity
- Contributors need BigQuery credentials to run `dbt run` locally

### Neutral

- If the project scales, match/intermediate models may need further subdivision (e.g., `match/cnpj`, `match/cpf`)
- Future: incremental models (`materialized='incremental'`) to handle large source tables efficiently

## Rejected Alternatives

### No dbt (raw SQL scripts)

**Rejected**: dbt provides dependency management, testing, documentation, and a standard project structure. Raw SQL scripts would require reinventing these features.

### dbt-duckdb

**Rejected**: DuckDB is excellent for local analytics, but BigQuery is the chosen transform engine (ADR-0001). `dbt-duckdb` would require porting Base dos Dados sources to DuckDB or writing glue code, losing the BD integration advantage.

### dbt only in a private `data-analysis` repo

**Rejected**: Would split transformation logic from presentation code, making versioning and cross-references harder. The freeze list and transformation logic are not sensitive; keeping them public allows community contributions and transparency.

### Query BigQuery at Astro build time

**Rejected**: See ADR-0001. Querying BQ during HTML generation couples the site to BigQuery availability and increases build time. Pre-exporting Facts to R2 decouples concerns.

### Export Facts as a single monolithic JSON

**Rejected**: Cloudflare Pages has a 25 MiB per-file limit. A monolithic JSON would exceed this limit as the freeze grows. Per-person JSONL files are smaller and allow Astro to load only the Facts needed for each dossier page.
